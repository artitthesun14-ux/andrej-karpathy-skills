# /handoff

หลักการ: ส่งต่องานให้ session ถัดไปทำต่อได้ทันที โดยไม่ต้องไล่อ่านบทสนทนาทั้งหมด และไม่สร้างข้อเท็จจริงที่ไม่มีหลักฐาน

## Purpose

สร้าง Handoff ที่ตอบให้ได้ว่า:

- กำลังทำอะไร และเป้าหมายสุดท้ายคืออะไร
- ทำอะไรเสร็จแล้ว และอะไรยังไม่เสร็จ
- มีปัญหาอะไรเกิดขึ้นใน session นี้หรือ session ก่อนหน้า
- ทดลองแก้อะไรไปแล้ว ผลเป็นอย่างไร และวิธีไหนใช้ได้จริง
- มีการตัดสินใจหรือข้อจำกัดอะไรที่ session ถัดไปต้องรักษาไว้
- ควรเริ่มทำอะไรต่อเป็นอันดับแรก และจะรู้ได้อย่างไรว่างานสำเร็จ

## When to use

- ก่อนจบ session หรือเปลี่ยนไปทำงานอื่น
- เมื่อ context เริ่มยาวและต้องเริ่ม session ใหม่
- หลังแก้ปัญหาซับซ้อนหรือทดลองหลายวิธี
- เมื่อมีหลาย session ทำงานต่อเนื่องบน repository หรือโปรเจกต์เดียวกัน
- เมื่อผู้ใช้ขอให้สรุปสถานะหรือเตรียมส่งต่องาน

## Operating rules

1. **ตรวจหลักฐานก่อนสรุป** ใช้บทสนทนาปัจจุบัน ไฟล์ handoff ที่มีอยู่ สถานะ Git, diff, commit history, TODO และเอกสารโปรเจกต์ที่เกี่ยวข้องตามความจำเป็น
2. **ห้ามอ้างว่ารู้ session อื่น หากไม่มีข้อมูลให้ตรวจ** ค้นหา handoff log หรือบันทึกเดิมก่อน หากไม่พบ ให้ระบุว่าไม่พบหลักฐานของ session ก่อนหน้า ห้ามแต่งเหตุการณ์หรือการแก้ไขขึ้นเอง
3. **แยกสถานะความแน่นอน** ใช้ `CONFIRMED`, `REPORTED`, `HYPOTHESIS` หรือ `UNKNOWN` เมื่อมีโอกาสสับสนระหว่างข้อเท็จจริงกับคำบอกเล่าหรือข้อสันนิษฐาน
4. **บันทึกปัญหาเป็นวงจร** ระบุอาการ สาเหตุที่ยืนยันแล้วหรือยังไม่ยืนยัน วิธีที่ลอง ผลลัพธ์ วิธีแก้สุดท้าย และสถานะปัจจุบัน
5. **เก็บวิธีที่ไม่สำเร็จด้วย** บันทึกเฉพาะวิธีที่ลองจริง พร้อมผลและเหตุผลที่ไม่ควรลองซ้ำ หากทราบ ห้ามนำเสนอวิธีที่ยังไม่ได้ทดลองเหมือนเป็นผลทดสอบแล้ว
6. **บันทึกการตัดสินใจและเหตุผล** โดยเฉพาะข้อจำกัด สถาปัตยกรรม สิ่งที่ตั้งใจไม่ทำ และทางเลือกที่ถูกปฏิเสธ
7. **ให้ session ถัดไปเริ่มทำงานได้เลย** เขียน Next Action เป็นคำสั่งเฉพาะเจาะจง เรียงตามลำดับ พร้อมไฟล์หรือบริเวณที่ต้องเริ่มตรวจ และ Success Check
8. **สั้นแต่ไม่เสียสาระ** ตัดเรื่องเล่าซ้ำ ๆ ออก แต่ห้ามตัดข้อมูลที่จำเป็นต่อการทำงานต่อ การ debug หรือการตรวจสอบ
9. **อย่าเปลี่ยนงานโดยไม่ได้รับอนุญาต** Skill นี้มีหน้าที่ตรวจ สรุป และบันทึก handoff ไม่ใช่ refactor โค้ดหรือแก้ปัญหาเพิ่มเติม เว้นแต่ผู้ใช้สั่งแยกต่างหาก
10. **ไม่เปิดเผย Secrets** ห้ามคัดลอก token, password, private key, ข้อมูลส่วนบุคคล หรือค่า environment ลับลงใน handoff ให้บันทึกเพียงชื่อตัวแปรหรือวิธีเข้าถึงอย่างปลอดภัย
11. **อย่า stage หรือ commit อัตโนมัติ** ห้ามใช้ `git add .`, commit หรือ push เว้นแต่ผู้ใช้สั่งชัดเจน

## Workflow

### 1. Establish current state

ตรวจข้อมูลที่เกี่ยวข้องเท่าที่จำเป็น:

- เป้าหมายและคำขอล่าสุดของผู้ใช้
- สิ่งที่เสร็จและสิ่งที่ยังค้างจากบทสนทนาปัจจุบัน
- ไฟล์ที่เปลี่ยนและ diff ที่เกี่ยวข้อง
- `git status` และ commit ล่าสุด หากเป็น Git repository
- handoff เดิม, decision log, issue log หรือ TODO ที่เกี่ยวข้อง
- ผลการทดสอบหรือ validation ที่เกิดขึ้นจริง

อย่าอ่านทั้ง repository โดยไม่จำเป็น ให้ค้นเฉพาะส่วนที่เกี่ยวข้องกับงานนี้

### 2. Build an issue and fix ledger

สำหรับปัญหาสำคัญแต่ละข้อ ให้บันทึก:

- **Issue:** อาการหรือสิ่งที่ผิด
- **Impact:** กระทบอะไร
- **Status:** OPEN, INVESTIGATING, FIXED, MITIGATED หรือ BLOCKED
- **Cause:** สาเหตุที่ยืนยันแล้ว หรือสมมติฐานที่ยังต้องตรวจ
- **Attempts:** วิธีที่ทดลองจริงและผลที่เกิดขึ้น
- **Resolution:** วิธีแก้ที่ใช้ได้จริง หรือเหตุผลที่ยังแก้ไม่ได้
- **Evidence:** ไฟล์, diff, คำสั่ง, error หรือผลทดสอบที่รองรับ
- **Follow-up:** สิ่งที่ยังต้องตรวจหรือทำต่อ

รวมปัญหาจากหลาย session เฉพาะเมื่อมีหลักฐานจาก handoff log, commit, issue tracker หรือบันทึกที่เข้าถึงได้ ระบุ session/date เมื่อทราบ หากไม่ทราบให้ใช้ `date unknown` แทนการเดา

### 3. Capture decisions and constraints

บันทึกการตัดสินใจที่มีผลต่อการทำงานต่อ เช่น:

- เหตุผลที่เลือกแนวทางหนึ่ง
- ข้อจำกัดทางเทคนิคหรือผลิตภัณฑ์
- สิ่งที่ผู้ใช้ระบุว่าไม่ต้องการ
- convention ของ repository
- dependency หรือ integration ที่ต้องคงไว้
- แนวทางที่ลองแล้วไม่ควรทำซ้ำ

แยก user decision ออกจากข้อเสนอของ agent ให้ชัดเจน

### 4. Write the handoff

ใช้โครงสร้างต่อไปนี้ โดยข้ามหัวข้อที่ไม่มีข้อมูลได้ แต่ห้ามแต่งข้อมูลมาเติม:

1. Goal and Success Criteria
2. Current Status
3. Completed
4. Issues and Fixes
5. Attempts That Failed or Were Rejected
6. Decisions and Constraints
7. Files Changed
8. Validation and Evidence
9. Open Questions and Risks
10. Next Actions, in priority order
11. Exact First Step for the Next Session
12. Ready-to-paste Continuation Prompt

Continuation Prompt ต้องมีบริบทเพียงพอให้ session ใหม่เริ่มได้ทันที แต่ไม่ควรคัดลอก handoff ทั้งหมดซ้ำอีกครั้ง

### 5. Persist without losing history

ก่อนบันทึก ให้ตรวจว่ามีรูปแบบหรือโฟลเดอร์ handoff อยู่แล้วหรือไม่ และใช้ของเดิมถ้าเหมาะสม

หากโปรเจกต์ไม่มี convention ให้ใช้ค่าเริ่มต้น:

- `.ai/handoff/current.md`: สถานะล่าสุดสำหรับ session ถัดไป
- `.ai/handoff/sessions/YYYY-MM-DD.md`: บันทึกของ session นี้ เพื่อรักษาประวัติ

กติกาการบันทึก:

- สร้างหรืออัปเดต `current.md` ให้เป็นสถานะล่าสุดที่อ่านง่าย
- เก็บบันทึก session แยกตามวันที่เพื่อไม่ให้ประวัติสำคัญถูกเขียนทับ
- หากมีไฟล์วันเดียวกันอยู่แล้ว ให้เพิ่มข้อมูลอย่างระมัดระวังหรือปรับปรุงรายการเดิมโดยไม่ทำข้อมูลที่ยังมีประโยชน์หายไป
- ห้ามคัดลอกข้อมูลเดิมซ้ำโดยไม่จำเป็น
- หากไม่มีสิทธิ์เขียนไฟล์ ให้แสดงเนื้อหา handoff พร้อมแจ้งว่าไม่ได้บันทึกลง disk
- อย่าอ้างว่าบันทึกสำเร็จจนกว่าจะตรวจสอบไฟล์ที่เขียนแล้ว

### 6. Verify the handoff

ตรวจสอบก่อนส่งมอบ:

- เป้าหมายและสถานะปัจจุบันชัดเจนหรือไม่
- ปัญหาที่แก้แล้วแยกจากปัญหาที่ยังค้างหรือไม่
- วิธีที่ไม่สำเร็จถูกบันทึกพร้อมผลหรือไม่
- มีการแยกข้อเท็จจริงออกจากสมมติฐานหรือไม่
- ไฟล์ที่เปลี่ยนและผลทดสอบตรงกับหลักฐานหรือไม่
- Next Action ทำได้จริงและเรียงลำดับแล้วหรือไม่
- session ใหม่จะรู้ว่าควรเริ่มจากตรงไหนโดยไม่ต้องถามซ้ำหรือไม่
- ไม่มี secrets หรือข้อมูลลับหรือไม่
- ไฟล์ handoff ที่บันทึกสามารถอ่านกลับได้หรือไม่

## Output format

ตอบผู้ใช้ด้วยสรุปสั้น ๆ:

- เป้าหมายและสถานะ
- ปัญหาหลักและวิธีแก้
- สิ่งที่ยังค้าง
- ขั้นตอนแรกของ session ถัดไป
- ไฟล์ handoff ที่สร้างหรืออัปเดต
- สิ่งที่ยังยืนยันไม่ได้

ไม่ต้องแสดงรายงานยาวทั้งหมดในแชตหากได้บันทึกลงไฟล์แล้ว เว้นแต่ผู้ใช้ขอให้อ่านรายละเอียด

## Success criteria

Handoff สำเร็จเมื่อ session ใหม่สามารถระบุได้อย่างถูกต้องว่าเกิดอะไรขึ้น ทำอะไรไปแล้ว อะไรได้ผล อะไรยังไม่ทราบ และควรทำอะไรต่อเป็นอันดับแรก โดยไม่ต้องเดาหรือทำซ้ำงานที่เสร็จแล้ว
